# 设计与业务语义说明

## 1. 头寸与现金流口径

### 1.1 支持的产品

| 产品 | 方向 | 合同现金流 | 压力行为现金流 |
| --- | --- | --- | --- |
| `DEMAND_DEPOSIT` 活期存款 | 负债 | 无固定到期日，合同阶梯不产生具体日期现金流 | `RUNOFF`：按分层流失率流出 |
| `TERM_DEPOSIT` 定期存款 | 负债 | 到期日本金 + 按 ACT/365F 的一次性利息流出 | `EARLY_REDEMPTION`：窗口后才到期部分按比例提前支取 |
| `WHOLESALE_FUNDING` 批发融资 | 负债 | 到期日本息流出 | `ROLLOVER`：到期部分按滚续比例回流，抵消流出 |
| `UNDRAWN_CREDIT_LINE` 未提取授信 | 表外或有 | 无 | `DRAWDOWN`：按分层提取率流出，受授信到期日截断 |
| `SECURITY_HOLDING` 持有证券 | 资产 | 到期按面值流入 | `LIQUIDATION`：按 `NONE/HQLA/ALL` 口径在第 1 天折价变现 |
| `LOAN_RECEIVABLE` 贷款回款 | 资产 | 到期还本付息，或按摊还计划逐期流入 | `PREPAYMENT`：提前还款比例流入 |

通用约定：

- 金额一律使用 `int64` 最小货币单位（如分），比率为 `float64`（如 0.03）；
  利息按 ACT/365F 计算，四舍五入（半数远离零），跨平台结果一致。
- 日期使用与 UTC 时区无关的日历日（YYYY-MM-DD），非法日历日（如 2026-02-30）直接拒绝。
- 每笔展开后的现金流都带 `Basis` 口径标签：
  `CONTRACTUAL / RUNOFF / EARLY_REDEMPTION / DRAWDOWN / PREPAYMENT / ROLLOVER / LIQUIDATION`，
  快照保留完整明细，结论可逐笔解释。
- 通知期 `NoticeDays > 0` 时，相关现金流日期整体顺延通知期。

### 1.2 时间桶与确定性

- 合同现金流按“日历日”分桶；同一头寸同一天、同一口径的多笔现金流先排序再求和，
  结果只取决于头寸与现金流集合，**与登记顺序无关**（见 `ladder.mergeSameDay`）。
- 任意时点净现金流：`NetCashFlowAt(from, at)` 返回 `(from, at]` 区间带符号净流；
  `from` 为零值时从最早现金流日累计。流入为正、流出为负。

### 1.3 输入拒绝原因（不静默跳过、不按零处理）

| 原因码 | 触发条件 |
| --- | --- |
| `MISSING_FIELD` | 必填字段缺失（ID/币种/交易对手/方向/起息日/到期日/摊还计划等），或 `CORRECT` 目标不存在 |
| `INVALID_AMOUNT` | 金额 ≤ 0、市值为负、利率为负或明显口径错误 |
| `INVALID_TERM` | 期限矛盾、到期日早于起息日、摊还计划非严格递增/超出到期日、HQLA 级别非法等 |
| `UNKNOWN_PRODUCT` | 未知产品类型 |
| `DIRECTION_MISMATCH` | 方向与产品口径不符（如存款标成资产） |
| `DUPLICATE_POSITION` | 同批次内重复 ID；或跨批次以 `REGISTER` 再次登记已存在头寸 |
| `CURRENCY_MISMATCH` | 头寸币种与引擎统一币种不同 |
| `INVALID_DATE` | 非法日历日 |

重复登记与显式更正的区分：

- `REGISTER`：新登记；ID 已存在即按 `DUPLICATE_POSITION` 拒绝，绝不静默覆盖。
- `CORRECT`：显式更正；ID 必须已存在，否则拒绝。更正为整体替换。

一个批次中任何一笔头寸非法，**整批拒绝**，合法头寸也不会半可见
（错误以 `RejectList` 聚合返回，逐笔可区分）。

## 2. 情景与版本语义

### 2.1 参数与分层

情景参数全部按头寸 `Segment` 分层（缺省分层为 `DEFAULT`）：
`runoff_rate / early_redemption_rate / wholesale_rollover_rate / drawdown_rate /
prepayment_rate / security_haircut / liquidate_level / runoff_profile`。

- 取值规则：先精确匹配头寸分层，再回退 `DEFAULT`；两者都缺失即拒绝
  （“引用未定义假设”），不按零处理。
- 比率必须在合法区间（折价率必须 < 1，100% 折价视为自相矛盾）；
  `liquidate_level ∈ {NONE,HQLA,ALL}`，`runoff_profile ∈ {FLAT,DAY1}`，否则拒绝。
- 行为曲线：`FLAT` 在压力窗口内逐日均摊（余数确定地加到最后一天，保证总额精确）；
  `DAY1` 全部落在基准日 + 1 天。

### 2.2 继承、叠加与覆盖

- 情景可声明 `Parent`（父情景），父版本 `ParentVersion=0` 表示**发布时刻**最新版本，
  发布时即被固定为具体版本，写入解析结果的版本链 `Chain`。
- 覆盖规则：分层 map 按“分层键”合并；子情景同分层的非 nil 值覆盖父值，
  未覆盖分层继续继承父值；继承链上的所有参数不得在不同版本间混算。
- 继承引用未定义父情景直接拒绝；继承链解析包含环检测（防御性，
  在“父必须先发布”的模型下正常使用不会出现环）。

### 2.3 不可变版本与复现

- 情景以 `(Name, Version)` 标识；**发布后不可变**，重复发布同名同版本拒绝。
  修改参数只能用新版本；旧版本定义与解析结果永久保留。
- 每个快照固定 `(状态序号, 情景名, 情景版本, 基准日, 窗口)`。
  用旧版本情景重算得到与历史一致的指标；新版本情景不会改写任何历史结论。

### 2.4 指标口径

- `TotalInflows / TotalOutflows`：窗口内每日压力流入/流出绝对值合计；
  `NetOutflow = max(流出-流入, 0)`。
- `LCR = HQLA调整后价值 / NetOutflow × 100%`；
  HQLA 只计入情景允许变现且标记为 HQLA 的证券，按级别系数
  （一级 100%、2A 85%、2B 50%）与分层折价率调整；`NetOutflow=0` 时 LCR 记为 -1（不适用）。
- `SurvivalDays`：自基准日起累计净现金流保持 ≥ 0 的完整天数；
  并给出首个累计净流出日 `SurvivalBreachDate`。

## 3. 批次、快照与更正规则

### 3.1 原子批次与状态

- 写入单位为 `Batch`（全局唯一 `BatchID`）。应用时在写临界区内完成
  “校验 → 折叠 → 持久化 → 原子发布”；读侧通过 `atomic.Pointer[state]`
  拿到不可变状态快照，**永远读不到只应用了一半的批次**。
- 每个状态带单调递增 `Seq`；快照记录其依据的 `StateSeq`。

### 3.2 幂等、回填、冲正与恢复

- **幂等回放**：重复提交相同 `BatchID` 返回 `Idempotent=true` 且状态零变化，
  绝不重复计数（同批次内重复 ID 仍属于脏数据，被拒绝）。
- **回填**：`PostedAt` 可以是历史日期，仅用于审计，不改变状态折叠顺序
  （顺序由应用 `Seq` 决定），因此回填结果确定。
- **冲正**：`ReverseBatchID` 指向目标批次；目标不存在或已被冲正均明确拒绝。
  冲正只移除“当前仍归属于目标批次”的头寸；已被后续 `CORRECT` 更正的头寸
  保留其更正后版本（更正优先于冲正）。被移除内容进入墓碑区。
- **恢复（对冲正再冲正）**：对冲正批次再冲正，从墓碑区确定性还原被移除头寸；
  若该头寸之后已被重新登记/更正，则不覆盖新内容。

### 3.3 快照不可变

- 已发布快照按快照键归档，永不被后续写入/更正原地修改；
  更正只会产生新 `Seq` 上的新版本快照。可用 `GetSnapshot` 按原参数取回。
- 同步 `Compute` 基于“调用瞬间已发布的完整状态”；
  异步 `PublishAsync` 可指定 `MinStateSeq`，通过条件变量等待目标状态后计算，
  并经 channel 回执，全程不使用 sleep 轮询。

## 4. 并发一致性模型

- **单写多读 + 不可变状态（copy-on-write）**：批次应用由写互斥串行化；
  每次写入克隆状态、修改新副本、`atomic.Pointer.Store` 整体发布。
- 读路径（合同阶梯、任意时点净流、同步/异步计算）只读不可变快照，**不加写锁**；
  耗时计算在独立 goroutine 完成，不阻塞其他查询与写入。
- 后台等待使用 `sync.Cond` 广播状态序号，避免 sleep 轮询；
  并发重算由信号量限 4，防止无界 goroutine。
- 一致性结论：状态序号单调不减；同一状态 + 同一情景版本 + 同一基准日/窗口
  必然产生同一快照（头寸按 ID 排序、现金流按日期/头寸/口径排序）。

## 5. 本地持久化

- 可选 `FileJournal`：每个批次一行 JSON 追加到本地文件（NDJSON），
  `Flush + fsync` 保证单条落盘；仅依赖标准库与本地文件系统。
- `engine.ReplayJournal` 按日志顺序重放到新引擎；批次幂等保证重复回放安全。
